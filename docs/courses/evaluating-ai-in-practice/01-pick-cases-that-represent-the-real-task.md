## What you will learn

Build a small case set with typical, ambiguous, and out-of-scope requests.

## Choose a case that can reveal a weakness

Ben’s first three examples are routine meeting reminders. None contains a canceled plan or an unresolved detail.

Sample typical work and add cases a polished draft could get wrong. For example, include a notice with no confirmed date, one with a late change, and one with private detail that should stay out.

## How it works

A useful comparison begins with real work patterns. Choose cases that expose different demands rather than multiple versions of the easiest example. Define the intended answer or decision from a trusted source before testing. Replace personal information with invented equivalents.

### Build a comparison set from the work people actually do

Start by observing a few real tasks. Describe both frequent patterns and failures that matter, then create safe examples that preserve those conditions. Use the same cases with your existing process and with the tool. Give both access to the same authoritative facts and time to arrive at an accepted result.

For announcements, a reasonable small set might include a routine notice, a late correction, a notice that must omit private information, and one with a still-unknown location. Assign each case an expected behavior. The expected output can be a question or handoff if the source does not establish an answer.

Keep these cases aside once you start changing the workflow. If you fix the draft after seeing all the cases and then report the same cases as proof, you are measuring how well you handled familiar examples. Exercise the revision on a fresh sample before making a broader recommendation.

## Worked example

For meeting summaries, a routine agenda, an unresolved decision, and a confidential item exercise three different expectations. Your examples should preserve uncertainty and omit the confidential item from public notes.
